FSAD Training · Section 1

Workflow Orientation

Six phases, one loop. Spec-driven development with Claude Code is a tight feedback cycle where every phase produces a checkable artifact before the next one starts.

01 — The Loop

Research → Spec → Plan → Implement → Verify → Iterate

Each phase narrows ambiguity. You leave it with an artifact you can point at — not a vibe, not a hand-wave. The loop closes when iteration produces no new questions.

🔍

1 — Research

Map the territory. What exists, what's known, what's unknown. Output: a research note that anchors every decision downstream.

📐

2 — Spec

Lock what we're building and why. Falsifiable requirements, no implementation. Output: a spec the team agrees on.

🗺️

3 — Plan

Decide how. Decompose into ordered tasks, name files, surface unknowns. Output: a plan you could hand to anyone.

⚙️

4 — Implement

Execute the plan. Atomic commits, one task at a time. Output: working code that traces back to the spec.

✅

5 — Verify

Prove it works against the spec, not against itself. Tests, manual checks, edge cases. Output: a verification report.

🔁

6 — Iterate

What did we learn? Update the spec, queue the next loop. Output: a clean handoff into the next phase or back to research.

The artifact is the contract. If you can't point at one, you skipped a phase. FSAD discipline
02 — Why It Matters

The Cost of Skipping Phases

Every phase you skip becomes a guess the agent has to make for you — usually badly, usually expensively, usually only visible once the code already exists.

⚠ Skip the spec, the agent invents one
It will ship something that compiles, runs, and is wrong. The wrongness is implicit, in the gap between what you meant and what it inferred. Each downstream phase amplifies the gap.
⚠ Skip the plan, the agent improvises
Improvisation produces sprawling diffs that touch files you didn't expect. Reviewability collapses. Atomic commits become a single 2,000-line PR.
✓ Run the loop, the agent stays on rails
With a spec and a plan in hand, implementation is mechanical. You spend your attention on the parts that need a human — the spec and the verification — and let the agent compress the parts that don't.
03 — Getting Started

How to Get Started

You don't need every tool. You need the discipline of producing an artifact at each phase. The tooling is downstream of the discipline.

→ The minimum viable loop
A research note (even one paragraph), a spec (even a checklist), a plan (even a numbered list), code, a verification pass (even a smoke test), and a follow-up. That's the loop. Tools come second.
→ Where Claude Code fits
Claude Code is the agent that executes phases 3–5 well, and helps draft phases 1–2. Sections 2 and 3 cover how to launch it; section 4 walks the loop with real artifacts.
FSAD Training · Section 2

Claude Code Basics

Five things to know before you press enter: how to launch, how permissions work, how to pick a model and effort level, how to read the statusline, and how to manage your context window.

01 — Launching

Launch

Claude Code runs in your terminal. From any project directory, type claude and you're in. The session inherits the cwd as the project root.

cd ~/path/to/project
claude
→ First-time setup
Run /login to authenticate, then /init from the project root to generate a starter CLAUDE.md — the file Claude reads on every session to understand your project.
02 — Permissions

Basic Permissions

Claude asks before running shell commands or editing files. You can approve once, approve always for a category, or deny. Three knobs you'll care about:

Allow once

Approves the exact command this turn. Safest. Use it when you're unsure or the command looks unfamiliar.

Allow always

Approves the command pattern for the whole session and saves it to your settings. Use it for the routines you trust — npm test, git status, ls.

Deny

Blocks the command and tells Claude to try something else. Use it as a redirection signal, not just a refusal.

✓ Lean toward "allow always" for read-only commands
Approving every cat, grep, and ls by hand burns concentration. Save approvals for anything that writes, deletes, pushes, or hits a network endpoint.
03 — Model & Effort

Model & Effort Settings

Two dials: which model thinks, and how hard. Pick them up front; switch on the fly with /model when the task profile changes.

Model

Opus for hard reasoning, architecture, and gnarly debugging. Sonnet for everyday coding. Haiku for quick rewrites and simple chores.

Effort

Controls how much thinking the model does before responding. Default works for most tasks. Bump it for plans, specs, and reviews; lower it for mechanical edits.

→ Rule of thumb
If the task is "make it work," default effort. If the task is "decide what to do," raise effort. If the task is "rename this var across the file," drop it.
04 — Statusline

Reading the Statusline

The bottom-of-terminal status row tells you where Claude is, what it's doing, and what context it's burning. A glance is usually enough.

Model + effort

Confirms which brain you're talking to. If the answer feels off, check this first — you may be on a smaller model than you think.

Context window

How full the conversation is. When it nears capacity, run /compact or /clear before asking for anything that needs the full picture.

Permission mode

Default, accept-edits, plan, or bypass. Tells you at a glance whether actions still need approval.

Working directory

Sanity check. If you're in the wrong directory, fix it before any command runs against the wrong project.

⚠ Watch the context bar
Once it turns yellow, you're a few turns from auto-compaction. Compact at a natural pause, not mid-task — the summary is more accurate when the current thought is wrapped.

Customizing the statusline

Ask Claude to configure it for you — it reads and updates your settings file directly. Three common setups:

05 — Context Window

How to Manage Your Context Window

Every Claude session has a fixed token budget. When it fills, Claude starts forgetting earlier turns. Three commands let you stay in control — check, compact, or clear — before the window manages you.

/context

Prints a breakdown of what's loaded and how many tokens each source is consuming. Use it whenever an answer feels like Claude is missing something.

/compact

Summarizes the conversation in place and replaces history with that summary. Run it at a natural pause — mid-task summaries lose detail.

/clear

Wipes conversation history entirely. Best when the current thread is done or so polluted that a clean slate is faster than compacting.

→ Use /context to diagnose surprising answers
If Claude gives an answer that feels off — wrong file, outdated assumption, missing constraint — run /context first. You'll often see that the relevant file wasn't read, or the system prompt is consuming most of the budget.

06 — CLAUDE.md

Your Project's Persistent Memory

CLAUDE.md is loaded into every session automatically. It's where you tell Claude about your project conventions, preferred stack, what not to do, and how you like to work — so you don't repeat yourself every session.

→ Generate a starter with /init
Run /init from the project root and Claude will inspect the repo and draft a CLAUDE.md tuned to what it finds. Edit it from there — it's just markdown.
✓ Example CLAUDE.md
The file below is a real CLAUDE.md from a live project. Note the three parts that carry the most weight: workflow orchestration rules, task management conventions, and core principles.
Example artifact · CLAUDE.md
## Workflow Orchestration

### 1. Plan Mode Default
- Enter plan mode for ANY non-trivial task (3+ steps or architectural decisions)
- If something goes sideways, STOP and re-plan immediately — don't keep pushing
- Use plan mode for verification steps, not just building
- Write detailed specs upfront to reduce ambiguity

### 2. Subagent Strategy
- Use subagents liberally to keep main context window clean
- Offload research, exploration, and parallel analysis to subagents
- For complex problems, throw more compute at it via subagents
- One task per subagent for focused execution

### 3. Self-Improvement Loop
- After ANY correction from the user: update `tasks/lessons.md` with the pattern
- Write rules for yourself that prevent the same mistake
- Ruthlessly iterate on these lessons until mistake rate drops
- Review lessons at session start for relevant project

### 4. Verification Before Done
- Never mark a task complete without proving it works
- Diff behavior between main and your changes when relevant
- Ask yourself: "Would a staff engineer approve this?"
- Run tests, check logs, demonstrate correctness

### 5. Demand Elegance (Balanced)
- For non-trivial changes: pause and ask "is there a more elegant way?"
- If a fix feels hacky: "Knowing everything I know now, implement the elegant solution"
- Skip this for simple, obvious fixes — don't over-engineer
- Challenge your own work before presenting it

### 6. Autonomous Bug Fixing
- When given a bug report: just fix it. Don't ask for hand-holding
- Point at logs, errors, failing tests — then resolve them
- Zero context switching required from the user
- Go fix failing CI tests without being told how

## Task Management

1. **Plan First**: Write plan to `tasks/todo.md` with checkable items
2. **Verify Plan**: Check in before starting implementation
3. **Track Progress**: Mark items complete as you go
4. **Explain Changes**: High-level summary at each step
5. **Document Results**: Add review section to `tasks/todo.md`
6. **Capture Lessons**: Update `tasks/lessons.md` after corrections

## Core Principles

- **Simplicity First**: Make every change as simple as possible. Impact minimal code.
- **No Laziness**: Find root causes. No temporary fixes. Senior developer standards.
- **Minimal Impact**: Changes should only touch what's necessary. Avoid introducing bugs.

Slash Commands

The eleven commands you'll touch most. Type / in any session to see the full list — these are the ones worth committing to muscle memory.

01 — Reference

Daily Drivers

Grouped by what they do, not alphabetically. Memorize the four in the first row; the rest you'll learn by hitting them when you need them.

Context management

/clear

Wipes conversation history. Start fresh when context is wrong, polluted, or no longer relevant. Files and project state stay.

/context

Shows what's currently loaded — files, system prompt, memory. Use it when an answer feels surprising and you suspect Claude is missing something.

/compact

Summarizes the conversation in place. Use it when the context bar is getting full but the work isn't done — at a natural pause, not mid-task.

Workflow

/plan

Enters plan mode — read-only exploration with a written plan you approve before any edits happen. The single most useful command in this list.

/resume

Picks up a previous session by ID. Useful when a long task spilled across days, or when you want to fork from a known-good state.

/init

Generates a starter CLAUDE.md for the current project — Claude's persistent project memory. Run it once per repo.

Configuration

/skills

Lists installed skills — reusable capability bundles Claude can invoke. Browse to discover what's available without leaving the session.

/plugin

Manage plugins: install, configure, enable, disable. Plugins ship commands, skills, hooks, and agents as a unit.

/doctor

Self-diagnostic. Checks config, network, permissions, and known issues. Run this first when something feels broken.

Session

/login

Authenticate with your Anthropic account. You'll run this once per machine, and again whenever the token expires or you switch accounts.

exit

Quit Claude Code. No slash — just type it. Use Ctrl+C twice as the keyboard equivalent.

→ Discover the rest
Type / on its own to fuzzy-search every command — built-ins plus the ones your installed plugins add. Highest-leverage way to find a command whose name you can't quite remember.

FSAD Training · Section 5

Single-shot vs Spec-Driven

The contrast that motivates the whole loop, on one screen.

01 — How They Actually Differ

Two Loops, Side by Side

Single-shot prompting on the left: type, hope, repeat. Spec-driven, context-managed on the right: a coordinator dispatches sub-agents that read and write to a shared substrate of spec, context, skills, and memory — and the spec evolves with what they learn.

02 — Inside a Single-Shot Prompt

What Actually Happens Between Request and Response

A deterministic pipeline with one probabilistic step in the middle. The shape of this is why agentic, spec-driven workflows exist.

03 — Inside an FSAD Flow

What Happens When You Direct Agents Instead

Same model. Different scaffolding. Stateful, curated, tool-rich, and verifiable — by construction.

✓ The TL;DR
Single-shot is fast at first and slow at the end — you spend the savings on debugging what the agent assumed. Spec-driven feels slower at first and is faster at the end — the artifacts catch divergence while it's still cheap to fix.

01 — Skills in this Repo

The Skill Library

Sixteen skills for task management, planning, and review — copied verbatim from the FSAD Playbook's own skills/ directory, unchanged. Open the definitions section below to read any skill's full source.

Workflow Management
/do-task <ID>

Plan or execute any task

Mode-switching skill: if no task file exists it interviews you and writes the plan; if a plan exists it implements it, verifies every acceptance criterion, and marks the task complete.

plan mode execute mode AC verification
/add-task [title]

Capture a new task

Auto-detects the current project, finds the next task number, and adds a numbered entry to the todo file — then interviews you one question at a time to write the task detail file.

auto-numbered one-at-a-time interview
/ship-it

Wrap up a finished batch

Four sequential phases: README check, CHANGELOG versioning, completed-task cleanup, then commit + push + PR. Run after do-task marks one or more tasks done.

version bump commit PR
/ship

Short alias for /ship-it

Wraps up finished work, cuts a version, commits, pushes, and opens a PR — same flow as ship-it under a shorter name.

alias
/next

Pick the next open task and run it

Reads the project's todo file, finds the first unchecked item, and hands it straight to do-task. No arguments needed.

hands off to do-task
/ac <ID>

Verify acceptance criteria

Walks every unchecked AC in a task file, fans each out to an independent verifier subagent, adversarially refutes each PASS, and marks each passing criterion immediately.

progressive marks adversarial refuter
/estimate

Story point estimation

Estimates work items on a Fibonacci scale (1–21) using a three-factor rubric: complexity, effort, and risk. Accepts bullet lists, numbered lists, or free prose as input.

Fibonacci scale complexity + effort + risk
/set-context

Gather context before planning

Runs a codebase sweep — a graphify build/query when available, a manual repo sweep otherwise — then asks targeted questions and writes a single context.md. Doubles as plan's mandatory Phase 0.

context.md plan Phase 0
Specification & Planning
/plan

Plan a significant project or refactor

Guides a large epic/initiative or codebase refactor through five gated planning artifacts — project.md, architecture.md, roadmap.md, verification.md, instructions.md.

gated phases 5 artifacts
/prd [feature title]

Write a PRD or feature spec

Four-phase gated flow: Discovery (Analyst role) → Specify (PM role) → Technical Plan → Task decomposition. Produces spec.md, plan.md, and tasks.md in the project's planning/prd/ directory.

discovery interview spec.md tasks.md
/plan-review

Adversarially review an implementation plan

Reviews a plan (PR, branch, or planning doc) against its baseline spec/ADR — up to 7 parallel lenses, every finding verified against the repo before it survives, then a completeness critic loops until dry.

7 lenses baseline-diff
/spec-review

Adversarially review a spec or proposal

Reviews a written proposal (spec, PRD, RFC, design doc) rather than code — a steelman pass, up to 10 specialist lenses, adversarial validation that defaults to refuting findings, then a loop-until-dry completeness pass.

10 lenses defaults to refute
Review & Security
/code-review-team

Multi-agent code review

Dispatches 7 specialist reviewers in parallel (correctness, design, performance, maintainability, testing, API contract, security), then consolidates validator-confirmed findings into a severity-ranked REVIEW-REPORT.md with a merge recommendation.

7 specialists adversarial validation REVIEW-REPORT.md
/sec-review-team

Multi-agent security review

Picks a specialist roster based on detected stack signals (webapp, IaC, LLM-agent, container, backend, etc.) from a library of 13 specialists. Produces a severity-ranked REPORT.md with deduped root issues.

13 specialists stack-signal detection REPORT.md
/sec-review-fixes

Apply security fix PRs

Companion to sec-review-team. Takes a REPORT.md or findings.jsonl and produces fix PRs per finding — each with a regression test. Safeguards: branch-only commits, no force-push, clean working tree required.

per-finding PRs regression tests
Prompting
/prompt-improver

Strengthen a draft prompt

Rewrites a draft prompt intended for Claude into a stronger, more reliable one — specificity, role/system framing, XML-tag structure, multishot examples, chain-of-thought cues, explicit output formatting.

prompt engineering
